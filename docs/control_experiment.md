# 有 Skill / 无 Skill：同一份坏材料上的同条件对照

> 这一节回答一个我们之前**没有数据**的问题：**这套 Skill 到底有没有用？**
> 设计上尽量只留**一个变量**：同一平台、同一份材料、同一本任务书、同一套交付物契约、同一个自检脚本；
> 唯一差别是**有没有 `SKILL.md`**（方法本体：8 步工作流 / 6 条 Validation / 8 条 Failure modes / 第 7 步的命令）。
> 样本只有 1+1 组、单一材料、单一平台，**不能做统计显著性宣称**，只报告观察。

## 1. 两轮怎么跑的

| | **有 Skill** | **无 Skill（对照）** |
|---|---|---|
| 玻尔会话 | `35822cccea564cf59cf21` | `3f8b9c490d384432b0a65` |
| 提示词（逐字） | `science-space/prompt-turn1.md` | `science-space/prompt-control-without-skill.md` |
| 附件 | `SKILL.md`、`task-C.md`、`material-corrupted.md`、`check_agreement.py` | **去掉 `SKILL.md`**，其余三个相同 |
| 提示词里写了什么 | 装配命令 + 读 `cases/task-C.md` 与 `skill/SKILL.md` + 5 条硬要求 + 自检命令 | 装配命令 + 读 `cases/task-C.md` + 5 条硬要求 + 自检命令（**逐字相同，只删掉"读 SKILL.md"那一句**） |
| 最终答案（逐字） | `science-space/answer-turn1.md`（+ 二轮 `answer-turn2.md`） | `science-space/answer-control-without-skill.md` |

**公平性上的自我约束**：任务书 `cases/task-C.md` 里本来就有全部硬性要求（引文逐字、分类纪律、不许编造数字、
数值核对 1%、5 条预期行为），**这些不是 Skill 带来的**，两边都拿到；自检脚本与命令也逐字相同。
→ 差异只剩"有没有那本方法本体"。

## 2. 观察到的结果

| 项 | 有 Skill | 无 Skill（对照） | 差在哪 |
|---|---|---|---|
| 结论词 | `transferable-with-changes` | "有条件可迁移"（同义） | **语义一致** |
| 结论条数 | 22（`paper-fact` 12 / `inference` 5 / `undetermined` 5） | 33（22 / 5 / 6） | 对照**更多**、更细 |
| `paper-fact` 占比 | 55%（自审 R-01 修正后 50%） | 67%（含 1 条列身份不成立 → 64%） | 对照**看起来更高** |
| 降级条数 | 8（5 结论 + 3 前置 `absent`） | 11（5 结论 + 6 结论 + 2 前置 `absent`） | 对照降级**更多** |
| 官方 checker | 0 标记（**跑 3 次**才过） | 0 标记（**首次即过**） | 对照**更省** |
| 5 条预期行为 | 第 1 轮自评 5/5 → **第 2 轮自审下调为 4 条 + ① 条部分做到** | 5/5（**未自我下调**） | 有 Skill 那轮**自我修正** |
| 表结构实测 | 表头 7 格 / 分隔行 8 段 / 1 行 9 格 / `#` 顺序 6,1,4,0,3,2,5 / `#4` 的 `time` 截断 | **逐项相同** | **独立复现一致** |
| 「第 4 行」的行号约定 | 指出"只有按 `#` 读才对" | 同样指出"只有按 `#` 读才对，按位置是第 3 行" | **独立复现一致** |
| CRLF 坑 | 二轮审计时踩到（`read_text` 把 CRLF 折成 `\n`，12 条 locator 全显示 L1） | **同样踩到**（text 模式读取 → `split('\r\n')` 只得 1 行 → IndexError） | **两个系统同一个坑** |
| 负控（证明 checker 不是空转） | 做了 | 做了 | — |
| **第一版负控的有效性** | **无效**（它的"拼接"恰好是原行的连续前缀，是脚本判对了） | **无效**（同一种错：我的"拼接"是真实连续前缀） | **两边都栽在同一处** |
| 给受损表的格子指派列名 | **没有** | **有**（`C-18 … row #4 CORE 0.71854`；`0.71854` 实为上游 `val_bpb`，见 `docs/column_semantics.md`） | **唯一可测的差别** |
| 耗时 | ≈5 分 34 秒 | ≈6 分钟（16:25→16:30 UTC） | 对照略慢但产出更多 |

## 3. 诚实的结论（含负面结果）

1. **在这份材料上，Skill 没有带来可测的整体质量提升。** 两边都做到了 5/5、checker 0 标记、
   同一组表结构实测；无 Skill 那轮**产出更多**（33 vs 22 条）、**降级更多**（11 vs 8）、
   **自检一次就过**（有 Skill 那轮改了 3 次才过）。**我们不能宣称 Skill 提效。**
2. **两边都栽在同一个负控设计错误上**：第一版"负控"其实不是负控（拼接出来的引文恰好是原文的连续前缀），
   于是"checker 0 标记"这件事本身需要被再质疑一次。**这是方法的盲点，不是某个模型的失误**——
   包内的 `scripts/check_agreement.py` 只验"连续子串"，不验"唯一命中"，这条已被云端那轮独立发现并补了一道自检
   （`logs/quote_check_v2.json`），而**两次负控的错误是同一个**。
3. **两边都踩了 CRLF 的坑**（读文本模式把行尾折掉 → 行号解析全错）。这条坑在包内 §4.1 有记录，
   现在它同时出现在两个独立系统上，说明**它是这类"逐行定位"方法的系统性风险，不是某次手滑**。
4. **Skill 唯一被测到的差别是"没有给受损表的格子指派列语义"**（见 §2 最后一行与 `docs/column_semantics.md`）。
   这条的证据强度有限：n=1、且无 Skill 那轮的最终 `claims.csv` 未随包，我们看到的是它会话可见的推理文本。
5. **样本与口径**：1+1 组、单一材料、单一平台；耗时含服务与共享主机负载。**不能做统计显著性宣称，
   也不能说"Skill 无效"**——只能说"这一次观察里 Skill 没有可测的整体优势"。

## 4. 这个对照为什么值得做（哪怕结论是负面的）

此前所有"5/5 做到、checker 0 标记"都只是**同一条流水线自己的自证**。有了这个对照，
至少可以说清楚：**我们主张的是"这套流程能产出可逐条复核的台账"（有机械证据），
而不是"它比不用它更好"（目前没有证据）**——这两句话的边界，之前我们没有数据去划。
