# 数字账本：本文的每个数字都能重算

> 机制侧的检查（引文命中、数值一致）只能证明**没有自相矛盾**；本账本证明的是**每个数字是怎么来的**。
> `scripts/verify_results.py` 从包内文件把账本重算一遍，只依赖标准库：

```bash
cd <材料包根目录> && python3 scripts/verify_results.py
```

预期结尾：`status: passed（15 条账本，0 条不符，1 条已知缺口）`；任一条**不符** → 退出码 1。
（「已知缺口」= 该项的材料未随包、在本包内不可复算，已如实标注，不算失败。）

## 最重要的一条：L-07 的自我修正

`runs/C-with-3/verdict.md` 的 **C29 列映射假设**写的是「数据行的 7 格按位置对应表头的 #/time/CORE/Description/Date/Commit/Contributors」，
并给出一个关键旁证：「`#0` 行里 `168 hours` 只可能是 time，`0.2565` 与正文 `0.256525` 相对误差 0.0098%」。

**作者侧用上游原表逐格对齐后发现，这个假设只对 1/7 行成立**：

- 损坏件的**损坏是逐行不同**的：`#0` 行被删掉的是 `val_bpb` 的占位符 `-`（所以它的第 3 格**确实是**上游的 CORE `0.2565`）；
  而 `#1`–`#6` 行被删掉的是**上游的 CORE 值**（所以它们的第 3 格装的是上游的 `val_bpb`：`0.74833 / 0.74645 / 0.71854 / 0.71808 / 0.71800 / 0.74504`）。
- 于是「表格第 3 格是 CORE」这句话**对 `#1`–`#6` 行不成立**；而 C29 的唯一旁证恰好来自**唯一成立的那一行**（`#0`），不能推广。

**这不改变结论词与降级集合**（受损表整表不作出处），但它改变一件事：
**受损表格的格子不能按位置指派列名**——这成了本 Skill 的第三条纪律（见 `docs/column_semantics.md`）。
它也是这次实践最值得带走的一课：**机械检查全绿（引文唯一命中、数值 1% 内、checker 0 标记），
不等于主张被材料支持。** 那个 0.0098% 的「一致」，数字没错、语义错。
