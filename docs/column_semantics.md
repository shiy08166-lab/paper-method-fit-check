# 列语义左移：损坏件里那列写着 CORE 的数字，其实不是 CORE

> 这是**作者侧独立核查**才发现的一层，三个执行系统（含我们自己那两次）都没看到。
> 证据只用包内两个文件：上游原表节选 `paper_materials/nanochat_README_leaderboard_upstream.md`
> 与合成损坏件 `paper_materials/nanochat_README_table_corrupted.md`。
> 复算脚本：`scripts/derive_column_semantics.py`（仅标准库）。

## 1. 之前我们只看到了"形状"不一致

损坏件的表头 7 个列名（`# | time | CORE | Description | Date | Commit | Contributors`）、
分隔行 **8** 段、数据行多为 7 格（1 行 9 格）。我们此前把它记成"**分隔行 8 段 vs 表头 7 格**"，
即一个列数对不齐的形状问题，并据此对**整表**降级（"整表受损，未做上游核验"）。

## 2. 逐格对齐后，形状问题的成因浮出来

把两边的表按 `#` 标签对齐、逐格比对（脚本输出）：**损坏件第 3 格（表头写着 `CORE`）装的
是上游第 3 格 `val_bpb` 的值**（7 行里 6 行一致），而上游第 4 格 `CORE` 的值
（`#1` 的 0.2585、`#2` 的 0.2690、`#4` 的 0.2571…）**在损坏件里根本不存在**：

| 损坏件格位 | 表头写的名字 | 实际装的是上游哪一列 | 一致行数 |
|---|---|---|---|
| 第 1 格 | `#` | `#` | 7/7 |
| 第 2 格 | `time` | `time` | 6/7（`#4` 的 time 被截断成 `2.`） |
| **第 3 格** | **`CORE`** | **`val_bpb`** | **6/7** |
| 第 4 格 | `Description` | `Description` | 7/7 |
| 第 5–7 格 | `Date`/`Commit`/`Contributors` | 同名 | 7/7 |

**唯一的例外是 `#0` 行**：上游 `#0` 的 `val_bpb` 是 `-`（原始 GPT-2 checkpoint 没有 val_bpb），
被删掉的是那个 `-`，所以 `#0` 行的 `0.2565` **确实是上游的 CORE 值**。
⇒ 损坏件里那一列**混着两种语义**：`#0` 行是真 CORE，`#1`–`#6` 行是 val_bpb。

**为什么损坏件自己提示了这一点却没人当回事**：分隔行仍保留着上游的 **8 段**（`val_bpb` 那一段还在），
表头被删掉了 `val_bpb` 这个**名字**，数据行少了**值**——于是"哪一格是什么"在损坏件内部**不可判定**。

## 3. 这个发现改变了什么（对我们自己的产出）

1. **受影响的是"给损坏表的格子指派列名"这种主张**。只要一条结论说"该行的 CORE 是 X"，
   它对 `#1`–`#6` 就是**不成立**的——那一格是 val_bpb。
2. **我们自己的 C-with-3 没有犯这个错**（`runs/C-with-3/claims.csv` 的 C26/C27）——它们的措辞是
   "被破坏的表中**确有一行** d24 baseline 记录：3.04、0.74833、Jan 29 2026、348fbb3
   （整表受损，未做上游核验）"：只陈述**格值序列**，**不指派列语义**，
   且 `numeric_value` 取的是 `time`（3.04 / 1.65）这一列——它的列身份在两个表头下都无歧义。
   → 这条纪律是**方法本身带来的**，不是运气。
3. **玻尔云端那一轮也没犯**：它的 12 条 `paper-fact` 里，表格来源的三条（`#6` 行 1.65、`#1` 行 3.04、
   `#0` 行 0.2565）用的都是 `time` 与 `#0` 那条真 CORE；**整行没碰 `#4` 行**。
4. **但"无 Skill"的对照轮犯了**：它在会话可见的推理里把 `#4` 行写成
   `C-18 … row #4 **CORE** 0.71854`，即把 `0.71854`（实为 val_bpb）当成了 CORE 值并写进 `numeric_value`。
   （它的最终 `claims.csv` 未随包，此处依据为会话可见的推理文本；`answer-control-without-skill.md` 的最终答案里
   也能看到它对 `#4` 行的处理。）

## 4. 正确的处置（本 Skill 该补的一条）

**受损表格里的格子，不能指派列名**——因为该表的列身份已被破坏且不可从文件内部恢复。
正确写法二选一：
- 只陈述"该行有这些格值"（如我们 C26/C27 的写法），把列身份留给 `undetermined`；或
- 若必须谈某一列，只用**列身份在两个表头下都一致**的那一列（`#` 与 `time`），并说明理由。

这与已有的两条纪律并列（引文必须唯一命中；受损值不得补全）：
**第 ③ 条：受损表格的格子不得指派列语义。**

## 5. 为什么这一层三个系统都没看到

因为纪律要求"运行期**不读**上游 leaderboard 表格"（记录见公开仓库 `runs/C-with-3/logs/run_log.md`）：
一旦在运行期读了原表，"受损值可能被污染成已知答案"，整个降级机制就失去意义。
**代价是：运行期没有任何一个系统能自己发现列语义左移。**
它是**作者侧**用上游节选做独立对照才发现的——这正好说明一件事：
> **"引文命中唯一 + checker 0 标记"这类机械检查，只覆盖了问题的一层。**
> 机械检查全绿，不等于主张被材料支持。
