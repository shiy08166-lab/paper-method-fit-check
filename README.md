# 用 AI 判断「这篇论文的方法能不能搬到我这」

> `paper-method-fit-check` —— 一个把「方法适用性判断」变成可核验流程的 Skill
>
> 模型：MiniMax-M3.1-Flash ｜ 宿主：MiniMax Code（桌面版）｜ 全部运行离线、无外网请求

---

## 0. 五分钟速览

**我解决的具体问题**：读论文时最耗人的不是「看不懂」，而是**看懂了却不知道能不能用在我这**。这个判断每次读论文都会重来一遍，却几乎每次都靠人临时翻文档、临时猜，最后给出一个没有依据的「应该可以吧」。

**我的做法**：把它固化成一个 Skill。输入一篇技术文档 + 一组读者约束（算力、预算、数据规模、目标），输出四样东西——

1. **方法的硬前置条件**（compute / data scale / hyperparameters / hidden assumptions 四类齐全，每条必带原文定位；原文没说的显式记为 `absent` 并写明原因）
2. **关键结论逐条锚定到原文**（每条承重的结论都带可搜索命中的逐字引文 + 定位）
3. **原文事实 / 我的推断 / 尚不能确定**三类严格分开，不混为一谈
4. **一个四选一结论**（`transferable-as-is` / `transferable-with-changes` / `not-transferable` / `undetermined`）+ 适用边界 + 遗留问题（每个未决点写清「需要什么才能定」）+ 下一步该读哪张图哪一节

**实际效果**（同一份 nanochat 材料，两组独立公平配对）：

| | 无 Skill 侧 | 有 Skill 侧 |
|---|---|---|
| 结论数 | 44 / 28 | **78 / 68** |
| 显式标出的「原文没说」处 | 3 / 4 | **8 / 6** |
| 引文可程序化命中 | 70/70、72/72 | 60/60、52/52 |
| **单条结论累计 token 成本** | 197,100 / 236,873 | **84,614 / 85,598** |
| 「下一步」是否指到行号 + 具体未决点 | 否 / 否 | **是 / 是** |

两组有 Skill 侧的单条结论成本相差 **1.2%**，两组无 Skill 侧相差 **20%**——Skill 侧把产出成本**稳定地**压到约 8.5 万 token/结论，基线则在 20–24 万之间晃。**稳定性比幅度更能说明增益是真的。**

本文后面讲三件事：**这个判断难在哪**（§1）、**我把它拆成了什么流程以及每个设计取舍的代价**（§2）、**这套流程实际跑出来的结果和我踩过的 7 个坑**（§3–§4）。§5 是复现步骤，§6 是方法适用边界，§7 是迁移到玻尔科学空间的指南，§8 是来源与贡献说明。

## 0.5 阅读约定：三种陈述严格分标

本文所有陈述属于下面三类之一，**全文按此标记**，读者可据此判断每一句话该信到什么程度：

| 标记 | 含义 | 可核查方式 |
|---|---|---|
| **【原文】** | 论文/文档的**逐字**内容 | 给出行号与逐字引文；在 `paper_materials/` 的快照里搜引文即可命中 |
| **【AI】** | 模型（MiniMax-M3.1-Flash）的**输出**，未经我改写 | 原始轨迹在 `trace.md`；逐条产物在 `runs/*/` |
| **【判断】** | 我基于前两者的推理，**原文没有这么说** | 推理链写在 `runs/*/claims.csv` 的 `reasoning` 列；分类为 `inference` |

三者的边界在产物层面是**机器可查**的，不只是本文的措辞：

- `paper-fact` 行**必须**有 `quote`（`【原文】`），`inference` / `undetermined` 行的 `quote` **必须为空**（`【判断】`）—— 由 `scripts/check_agreement.py` 的 `P4c` 断言强制
- 每一处 `【原文】` 引文都经过「原始字节连续子串 + 命中次数为 1」的程序化校验
- 每一处 `【判断】` 都能在 `claims.csv` 里找到它依赖哪些 `paper-fact` 行

举个具体例子（§3.3 展开）：原文说「代码在 8×A100 节点上能正常跑，只是慢一点」——这是 **【原文】**；由此推出「读者 4 小时预算够不够，取决于 A100 相对 H100 的倍率，而原文没给这个倍率」——这是 **【判断】**，它的依据是原文那句里的"慢一点"没有量化。**原文没说倍率，读者不能自己脑补一个数**，这就是 §3.3 那 8 个空白点的来源。

## 1. 问题：这个判断为什么难

### 1.1 难在三个环节，不在「理解论文」

大多数人以为「判断方法能不能迁」是理解问题。真正卡住的是三件更具体的事：

**难点一：原文的数字都带隐含前提，而这些前提散落在正文、表格和代码里。**

以 nanochat 为例，它的招牌数字是「$48 / 约 2 小时 / GPT-2 级」。但这个数字的成立前提——8×H100 单节点、80GB 显存、bf16 默认路径、作者调好的 `D_REF`/`B_REF`——**没有一个写在数字旁边**。读者要做「4 小时 / $100 / 8×A100 能不能跑」这个判断，就必须把这些前提从正文、leaderboard 表格、`base_train.py` 的常量与断言里逐个挖出来对齐。

**难点二：「原文没说」和「我还没找到」必须被区分开。**

如果模型只是「尽量多列前置条件」，它会把「作者没提过但确实重要」的东西混进「作者明确说了」里，读者分不清哪些能直接引用、哪些需要自己验证。判断错了，结论就废了。

**难点三：引文转写会失真，而且失真是静默的。**

这是最实操、也最容易被忽略的一环。让我读 `nanochat_base_train.py` 的一行，我看到的是被渲染过的版本；我按行号数，可能数到空行；我把文件内容抄进引文，可能抄错空格。**结果是一条看起来很像原文、实际上根本不是原文的「引文」。** 读者的整个核查链条就断在这里。

### 1.2 为什么「给 AI 更好的提示词」解决不了

试过。提示词写得更长、要求更细，效果提升有限。原因在于这三类错误（前提散落、边界混淆、转写失真）都不是「模型不够聪明」，而是**流程没有强制约束**：

- 模型**能**猜，但流程没禁止它猜 → 于是它猜了
- 模型**能**编一句像样的话，但流程没要求可验证 → 于是它编了
- 模型**能**用肉眼数行号，但流程没要求字节级切片 → 于是它数错了

所以我的目标不是让模型更聪明，而是**让它更可核查**——把「你认为对」变成「你可以自己验」。

### 1.3 我给自己定的边界

这是一个**阅读判断**类 Skill，回答「能不能迁、要改什么、哪些结论只在作者设定下成立」。

它**不负责**真的把方法跑起来，也**不覆盖**「照着跑一遍并对齐指标」的复现工作。当材料不足以判断时，正确产出是 `undetermined` + 「需要什么才能定」，而不是一个看起来笃定的结论。

## 2. 方法：把判断拆成六个可验证的步骤

完整本体见 [`paper-method-fit-check/SKILL.md`](paper-method-fit-check/SKILL.md)（三段式：`Workflow` 8 步 / `Validation` 6 条 / `Failure modes` 8 条）。这里讲每一步的**动机和取舍**——尤其是那些看起来「多余」的设计。

### 2.1 硬前置条件四分类，且每条必带定位或显式 `absent`

四类是固定的：**compute / data scale / hyperparameters / hidden assumptions**。

「必带定位**或**显式标 `absent` 并写原因」这条是全流程最关键的约束之一。它的作用是**把「我不知道」变成一等公民**：

> 一条前置条件，如果我找不到出处，那它要么是我编的，要么是原文真没说——两种情况我必须说清楚是哪一种，而不是留空蒙混过去。

配套的是 `confidence` 字段：`stated` / `absent` / `inferred` 三态。「我推断出来的」和「原文说的」也必须分开。

**取舍**：这让产出变「难看」——一份报告里出现 6–12 条 `absent` 看起来像没做完。但实测下来，这恰恰是**最有价值的部分**：读者最需要知道的正是「哪些事作者没说」，因为那正是他必须自己补的坑。

### 2.2 结论三分类，`paper-fact` 必须带引文，`inference`/`undetermined` 的引文**必须留空**

`paper-fact`（原文确证）/ `inference`（我的推断）/ `undetermined`（尚不能确定）三分，且**后两类的 `quote` 字段必须为空**——这是脚本断言的（P4c），不是文字约定。

为什么不允许推断也带引文？因为一旦允许，模型就会**给推断配一段看起来相关的原文**，读者分不清「作者说的」和「作者说的 + 我加的」。留空是一种**强制标记**：`quote` 为空 = 「这条是我说的，去 `reasoning` 列看我怎么推的」。

### 2.3 引文必须是原文的**单一连续片段**

一条 `quote` 只能来自原文一处连续片段，**不许拼接**（Skill 的原文措辞是「Never stitch two non-adjacent spans into one quote」）。

为什么这条排在这么前面？因为它是**整条证据链的地基**：只要允许拼接，就能用两个毫不相干的片段凑出一句「原文支持」的话，而读者无法察觉。

配套的强制动作是**程序化校验**：引文由脚本从原始字节按锚点切片生成，并逐条验证「是原文的连续子串、命中次数为 1」。肉眼核对不算数。

**取舍**：写脚本切引文比手抄慢。但我在实际跑里手抄过一次，**5 条引文当场失配**——理由见 §4.1。这个脚本不是锦上添花，它是这个 Skill 能成立的前提。

### 2.4 数值一致性层：把「抄对了」变成「验过了」

每个引用数值都算相对误差，**超过 1% 必须写处置**（保留两个值 / 取保守值 / 记为原文不一致）。

这一层抓到的典型问题：README 正文写「~1.5 hours」，同文件 leaderboard 表写 `1.65 h`——**同一份原文内部就不一致**。不校验就直接引用，等于把矛盾传给读者。

### 2.5 结论固定四段结构

① 结论（四选一 + 理由）② 哪些是原文确证的 ③ 哪些是我的推断（写清推理过程）④ 遗留问题（每个写清「需要什么才能定」）。

**固定结构**的作用是强制覆盖：写第 ④ 段时你无法跳过「我还有什么没搞清」。第 ④ 段的每条要写成「需要 X 才能定 Y」的形式——这让它同时变成**下一步的行动清单**。

### 2.6 五个关键取舍

| 取舍 | 我选了 | 代价 |
|---|---|---|
| 硬前置条件缺出处时 | 显式 `absent` + 写原因 | 报告里出现 6–12 条「缺口」，看起来像没做完 |
| 结论的引文 | 只允许 `paper-fact` 带 | 推断部分显得「没证据」，需要靠 reasoning 列补 |
| 引文提取 | 字节级切片 + 程序化校验 | 比手抄慢，多写脚本 |
| 信息不足时 | 明确降级为 `undetermined` | 结论看起来不够干脆，读者要多读一段才明白边界在哪 |
| 产物形式 | 固定 5 个文件 + 固定四段 | 不灵活，无法为每个问题定制结构 |

## 3. 案例：nanochat 的 speedrun 能不能搬到 8×A100 / 4 小时 / $100

### 3.1 输入与读者约束

- **主文档**：`materials/A/nanochat_README.md`（karpathy/nanochat 官方 README 原文快照）
- **代码证据**：`materials/A/nanochat_base_train.py`
- **同作者的简化版**：`materials/A/autoresearch_README.md` + `autoresearch_train.py` / `prepare.py` / `program.md`
- **读者约束（写死在运行前）**：8 × A100 80GB；单次完整训练 ≤ 4 小时，云卡费用 ≤ $100；数据可下载（磁盘 ≥ 100GB），但下载时间需单独说明；不允许多机；**只要方法机制，不要复现最终数字**

素材是公开仓库原文快照，逐文件 SHA-256 记录在 `materials/A/source_meta.json`。

### 3.2 结论与理由

> **`transferable-with-changes`**
>
> 方法机制层（单一 `--depth` 旋钮自动推导全部超参、autoresearch 的固定 5 分钟预算 Agent 实验循环、单节点 8 卡训练）在读者的约束下可迁；但**作者给的那套具体配置不能照搬**。

理由三条，都能落到原文：

1. **FP8 是 H100 专属路径** —— 【原文】代码里明写 requires H100+，【判断】读者是 A100（SM80），必须显式关闭
2. **8×A100 上完整 speedrun 的墙钟时间，全部材料里没有任何数字** —— 【原文】作者对 A100 的全部说明只有「a bit slower」一句；【原文】速度榜的 1.65–3.04 小时**全部是 8×H100 口径**
3. **`runs/speedrun.sh` 缺席** —— 【原文】材料里没有这个文件，【判断】导致 nanochat speedrun 自身的数据配置与 token 预算无法核对

所以「直接跑作者的脚本，4 小时 $100 就行」这个直觉在材料层面就被三处证据顶住了。而【判断】**唯一能定论的办法不是继续读论文，是在 8×A100 上真跑一次 d12 档**，只取三个数：wall-clock、`tok/sec`、`train/mfu`——成本不到 1 小时。（这一步属于"读者自己动手"，不在本流程职责内，见 §6.2。）

### 3.3 「原文没说」的 8 个地方（本文最该被读的部分）

这是整个产出里最有价值的部分，因为它直接指向读者必须自己补的坑。**有 Skill 侧识别出 8 处，无 Skill 侧只有 3–4 处。** 表中「原文给了什么」一列是 **【原文】**，「因此什么定不了」是 **【判断】**——两者的分界正是这个 Skill 的核心机制。

| 编号 | 原文给了什么（【原文】） | 因此什么定不了（【判断】） | 为什么关键 |
|---|---|---|---|
| `PD-01` | 4e19 FLOPs 与 d24–d26 深度区间 | 没说用了多少 token | → 无法算真实数据需求 |
| `HA-11` | 「<80GB 时降参」的指引 | 没说 80GB 到底装不装得下 | → 直接决定会不会 OOM |
| `HA-13` | 分词器存在 | 没说 vocab 大小 | → 影响参数量与数据/参数比 |
| `PC-12` | 「a bit slower」 | 没给 A100/H100 的墙钟倍率 | → 4 小时预算换算成 A100 的关键系数 |
| `PC-16` | —— | `common.py` 不在材料内，`get_peak_flops` 取值未知 | → MFU 口径能否移植未可知 |
| `PC-D06` | speedrun 的存在 | 没说 token 预算与数据集 | → 影响可复现性 |
| `PC-D07` | 数据下载链路存在 | 没说单 shard 字节数 | → 题面要求「下载时间需单独说明」 |
| `PC-A07` | —— | `runs/speedrun.sh` 缺席 | → 数据与预算无法核对 |

无 Skill 侧虽然把**代码常量与断言**挖得更细（`~/.cache/autoresearch` 缓存目录、`total_batch_size` 整数倍断言、`torch.compile` 首次编译开销），但**没有一篇是「原文没说」的**——它默认「作者没提 = 不重要」。两组恰好互补，这也是为什么召回率打平、而「边界识别」拉开了差距。

### 3.4 我核查了什么、怎么核查的

- **每条 `paper-fact` 都带逐字引文**，由脚本从原始字节切片生成并验证是连续子串（52/52、60/60、70/70、72/72 全部通过）
- **37 条带数值的行逐条算相对误差，全为 0**
- **自检器 0 标记**、退出码 0；验收标准 P1–P10 展开的 35 项检查全部 PASS
- **反向对照**：把一条引文里的 `8XH100` 故意篡改成 `8xA100`，自检器如期报错、退出码 1 —— 证明校验不是空转

### 3.5 局限（不掩饰）

- **模型快照版本无法取得**，只能以显示名 `minimax/MiniMax-M3.1-Flash` 声明
- **A100 的墙钟倍率没有权威值**：按 bf16 稠密峰值比折算 5.2–6.4 小时 / $125–154，按较宽松的 2.5× 吞吐折扣是 4.1–5.1 小时 / $99–121。两种算法同向，但都给不出可用于决策的点估计
- **素材是公开仓库的说明文档与源码，不是同行评议论文**
- **A100 的墙钟只能靠实测**：本 Skill 是阅读判断类，不负责跑训练，所以这一步必须读者自己做

## 4. 实践发现：8 个踩过的坑

每个发现都按同一结构写：**现象 → 证据 → 改进 → 验证 → 有效条件 / 失效条件**。最后一栏是我特意加的——一个改进如果不说明它什么时候不管用，它就只是运气好。

### 4.1 文件阅读视图对代码**不忠实**，而且它不报错

**现象**：用文件读取工具看 `nanochat_base_train.py`，部分行被**多渲染 4 个空格**，且 f-string `window_pattern='{args.window_pattern}'` 被渲染成插值后的 `'SSSL'`。我据此手抄的 5 条引文**全部失配**。

**证据**：`runs/A-without-1/logs/verification_report.json` 的 `quote_drafts_corrected`（6 条草稿与原文的逐条差异）；手抄草稿原样保留在 `runs/A-without-1/tables.py`，可与原文并排比对。

**改进**：不再从渲染视图取文本，改为按起止锚点从**原始字节**切片（`runs/A-without-1/quotes.py`），并对每条引文校验"是否为原文的连续子串"。

**验证**：改完后 70/70 条引文在原文里命中；有 Skill 侧走的是另一条独立代码路径（`runs/A-with-2/runs/scripts/extract_quotes.py`），得到同样结论。

**有效条件**：**只要**你打算把文本当证据引用，这条就适用。**失效**：纯自然语言、不需要定位的阅读不受影响——所以我只把它限定在"要出结论的段落"，不要求全文切片。代价是流程更重，这个取舍是故意的。

### 4.2 CRLF：多行锚点在 Windows 上会失配——而且是**不该**归一化

**现象**：材料是 CRLF 行尾，我按 LF 写的多行起止标记匹配不上，导致 4 条常量被归到**错误的文件**、另 1 条锚点有歧义。

**证据**：标记定义见 `runs/A-with-2/runs/scripts/quote_spec.py`；最终 65/65 条引文的校验结果见 `runs/A-with-2/runs/evidence_quotes.json`。

**改进**：用 `repr()` 打印原始行确认真实字节；引文库以**字节精确**的 `source.txt` 为准，**保留 CRLF 不做归一化**。

**验证**：这样原始字节切出的引文能被**朴素子串搜索**命中——评审不需要特殊工具就能核对。A 组两次运行独立得出同一结论；C 组三次独立运行在同一份 CRLF 材料上分别 46/46、32/32、28/28 命中。

**有效条件**：材料来自 Windows / CRLF 仓库时必须。**失效**：若上游是纯 LF，标记会自然匹配——也就是说这条不是"要不要归一化"的问题，而是"**别归一化**"。

### 4.3 `float('2.')` 静默等于 `2.0`：损坏的数值会被无声读成「2 小时」

**现象**：被截断的 `2.` 用 `float()` 读出来是 2.0，**不报错、不告警**，会被无声读成"2 小时"。

**证据**：`runs/C-with-1/verdict.md` 的实测记录与 C 组的 `extra-3` 自检项。

**改进**：数值一律带单位与来源定位；抽取后做数值域合理性检查；不确定就标 `undetermined`，**不猜补**。

**验证**：`extra-3` 检查项专门扫描"以 `2.` 开头"且"引用了受损行"的结论，结果为空；`extra-2` 另有一层扫描，确认受损表格的 4 条证据**没有**被提升为 `paper-fact`。

**有效条件**：**凡是解析可能被截断的数值都适用**。**失效**：原始数据已声明为结构化整数/浮点且有 schema 校验时，不存在这个风险。

### 4.4 声明块与实物对不上：连「构造件自己的说明书」都可能不可信

**现象**：我构造的异常材料顶部声明写"第 4 行被截断、第 6 行竖线错位"，但程序化列计数的实测是：截断行标签 **#4**、错位行 **#5**、**没有任何行标签为 #6**。

**证据**：`runs/C-with-1/runs/inspect_table_raw.json`（表头 7 格 / 数据行 7 行）、`runs/C-with-2/runs/logs/00_material_inspection.json`（同样 7 格 / 7 行）与 `runs/C-with-3/logs/corruption_audit.json`（同样 7 格 / 7 行）—— 三次独立运行给出一致的实测，且都与声明不符。

**改进**：一切以**实测**为准，不照抄声明——包括声明件自己的声明。

**验证**：C 组的 `extra-2` 检查项确认受损表格的 4 条证据**没有**被提升为 `paper-fact`；三次 C 运行的结论词完全相同（其中 C-with-3 是 prompt 逐字相同、输入逐字节一致的严格对称复测，见 §4.8）。

**有效条件**：**读任何材料都适用**，尤其当材料自带"作者说明"时。**失效**：无——这一条本身就是结论。

### 4.5 negative control：证明「校验器不是空转」的最短路径

**现象**：一个自检脚本如果永远返回"全部通过"，它和没有脚本没有区别——而我**无法**从"它说通过"推出"它真的在检查"。

**证据**：`runs/A-with-2/runs/negative_control.txt`：把一条引文里的 `8XH100` 故意篡改成 `8xA100`，检查器如期报错、**退出码 1**。

**改进**：任何自检脚本都配一条**反向用例**——故意喂一个应该失败的输入，确认它真的失败。

**验证**：negative control 的原始输出与正向结果**并列**留在运行产物里，不是单独的口头声明。

**有效条件**：有自检脚本就适用。**失效**：若检查器只做"存在性"判断（如文件在不在），反向用例无意义——所以它只对"检查器声称在验证内容"的情况有效。

### 4.6 两组独立配对：**稳定性**比幅度更有说服力

**现象**：单次对照的增益幅度会随这一次的运气浮动——我第一次无 Skill 侧是 197,100 token/结论，第二次是 236,873，**相差 20%**。如果我只做一组，就得拿这个数字下断言。

**证据**：`docs/comparison.json` 的 `cross_pairing_stability`。

**改进**：做**两组**独立配对，比较的是**两次 with_skill 之间的离散度**，而不是「一次 with vs 一次 without」。

**验证**：两组 with_skill 分别是 84,614 与 85,598（**相差 1.2%**），两组 without_skill 相差 20%——**基线在晃，Skill 侧不晃**。这比"提升了多少"更能说明增益是真的。

**有效条件**：**当"改善幅度"本身就是结论时**，必须做两组。**失效**：如果只想回答"有没有改善"、不打算对幅度下断言，一组够用——但结论的强度会低一档。

### 4.7 附：两个关于「AI 自述」的坑

- **子会话自报的耗时不可信**：一次运行在自己的笔记里写"约 74 分钟"，但会话记录 timestamp 差 661.9s、文件落盘跨度 623.0s——**两个客观口径都指向约 11 分钟**。→ 一切耗时以会话记录 / 文件时间戳为准；自述值原样保留不删，但在报告里注明差异。
- **官方自检脚本也可能寻址不到**：Skill 里写的相对路径与运行目录不一致时报 `Errno 2`。→ 失败要留痕、要换等价方式跑通，**且官方判定要原样保留、自己的补充核对另放一栏，不能覆盖官方结论**。

### 4.8 复现次数变多，结论条数反而变少——结构稳定，而展开粒度可变

**现象**：同一份材料、同一份 Skill，C 案例三次独立运行的结论条数是 **62 → 47 → 39**，**逐次递减**。只看数字，很容易判成"后面的复测质量在下降"。

**证据**：`runs/C-with-{1,2,3}/logs/agreement.json` 里官方 checker 三次都是 `findings_count=0 / all_passed=true`（`claims_checked` 分别是 62 / 47 / 39）；验收自检 14/14、14/14、**15/15** 全过；`undetermined` 绝对数 **10 → 9 → 7**（更克制，不是更宽松）。第三次 `runs/C-with-3/logs/verification.json` 另有 15 项自检，含 28 条引文的逐条原文命中校验。

**改进**：Skill 只冻结结论的**结构与出处要求**（三分类、必须有 `quote` 或显式标 `undetermined`、四段式结论、遗留问题必须写"需要什么才能定"），**不规定条数**——条数由每次会话自行决定展开粒度。因此评估复现质量时，判据应当是**结构一致 + 关键处置一致 + 官方 checker 0 标记**，而不是条数多少。

**验证**：第三次运行 `C-with-3` 是**严格对称复测**——prompt 与第一次**逐字相同**（仅改工作目录路径），`cases/`+`materials/`+`skill/` 四份文件与第一次**逐字节一致**（SHA-256 校验通过）。同一条件下仍得 39 条，说明条数差异来自**会话展开粒度**，不是条件不同带来的分歧。三次的结论词、5 条事先写定的预期行为、受损表格的处置（整张不作出处、`time`/`CORE` 进未决清单）全部一致。

**有效条件**：只要被复现物的**结构**被冻结（分类规则 + 引文可程序化命中 + 事先写定的验收标准），条数差异就不代表结论分歧。**失效**：当结构未被冻结（只说"再跑一遍看看"）时，条数与结论的差异**就是**质量差异——此时必须先冻结验收标准，再谈复现。


## 5. 复现：怎么自己跑一遍

### 5.1 环境与预算

| 项 | 值 |
|---|---|
| 宿主 | MiniMax Code（桌面版，本地运行时，Windows 11 / PowerShell 5.1） |
| 模型 | MiniMax-M3.1-Flash（**快照版本无法取得**，只能以显示名声明） |
| 工具 | 文件读写、Shell（PowerShell）、Python 3.14、grep / glob |
| 依赖 | **Python 3 标准库即可**，本仓库 `scripts/` 下全部工具无第三方依赖 |
| 预算 | 单次会话 ≤ 45 分钟；**全程离线**，0 次外网请求；未装 PyTorch、未下载数据集、未运行任何训练 |
| 人工参与 | 仅运行**之外**的三件：冻结任务与验收标准并记 SHA-256、取得题面资源、登记提交归属。**核心步骤全程无人工介入、无人工代做、无人工修正产出** |

### 5.2 操作步骤

**第 1 步**：把 Skill 放到 Agent 能读到的地方（挂载为可用 Skill，或直接把文件交给它）。本仓库：`paper-method-fit-check/SKILL.md`。

**第 2 步**：投喂下面这段提示词（把 `<>` 里的内容替换成你的即可，其余可原样用）：

```
读一下 paper-method-fit-check/SKILL.md，严格按它的工作流完成下面的任务。

【要回答的阅读问题】
<例：这份方法能不能在我的算力与预算下用？>

【输入材料】
- 主文档：materials/<file>.md
- 代码证据：materials/<file>.py
- 元数据（来源 URL / 取得时间 / SHA-256）：materials/source_meta.json

【读者约束（运行前写死，运行中不得修改）】
- 算力：<例：8 × A100 80GB>
- 时间 / 成本预算：<例：单次训练 ≤ 4 小时，云卡 ≤ $100>
- 数据：<例：可下载，磁盘 ≥ 100GB，下载时间需单独说明>
- 禁止：<例：不允许多机、不允许申请更多资源>
- 目标：<例：只要方法机制，不要复现文档的最终数字>
- 判定口径：<例：只关心方法能不能迁，不要求数字完全一致>

【硬性要求】
1. 严格离线，不发起任何外网请求。材料不足以判定的一律标 confidence=absent 或
   classification=undetermined，不要猜、不要补。
2. 每条 paper-fact 必须带可程序化命中的逐字引文（原文的单一连续片段）；inference 与
   undetermined 的 quote 字段必须留空。
3. 引文从原始字节切片生成，不要用肉眼数行号或手抄——文件读取视图对代码可能失真。
4. 每条前置条件必带 source_locator，或显式标 absent 并写明原因。
5. 数值逐条算相对误差，超 1% 必须写处置，不许删行。
6. 结论固定四段：结论 / 原文确证 / 我的推断 / 遗留问题；结尾给出下一步该读哪张图哪一节
   （指到行号 + 未决点编号）。
7. 中途失败、换方案、人工修正全部留痕到 runs/，不许删除。
8. 跑完用 scripts/check_agreement.py 自检，退出码必须为 0。
```

Agent 会自己产出 5 个文件：`preconditions.csv`、`claims.csv`、`evidence_index.json`、`verdict.md`、`logs/agreement.json`。

**第 3 步**：按 §5.3 的三个锚点判断结果是否符合预期。

> 注：`SKILL.md` 第 7 步的示例命令漏了必填的 `--source`，照抄会得到 argparse 的 `exit 2`
> （B 案例的独立复测实测到这一失败，原始输出见 `runs/B-with-2/runs/README.md` 的 F2）。
> 为不改动已锁定的 `skill_version`，我们没有改 `SKILL.md`，而是在 [`QUICKSTART.md`](QUICKSTART.md)
> 里给出补齐参数后的完整命令。

### 5.3 怎么判断结果是否符合预期（检查方法）

这一步是「复现价值」的关键——**读者要能自己判断结果对不对，而不是只能相信我**。

```bash
# 数值 / 引文一致性自检（仅标准库），退出码 0 = 全部通过
python3 scripts/check_agreement.py \
    --claims claims.csv --preconditions preconditions.csv \
    --source materials/nanochat_README.md \
    --tolerance 0.01 --report logs/agreement.json
```

配套的三条自查：

| 检查 | 期望 |
|---|---|
| 每条 `paper-fact` 的 `quote` 是否是原文连续子串 | 逐条命中，命中次数为 1 |
| `inference` / `undetermined` 的 `quote` 是否为空 | 必须为空（脚本 `P4c` 断言） |
| 数值相对误差 | ≤ 1%，超出的必须有处置记录 |

**判断结果是否合理的三个锚点**（而不是只看它「跑完了」）：

1. 结论词应该是 `transferable-with-changes`（不是 `transferable-as-is`——因为 FP8 是 H100 专属）
2. `absent` 的前置条件应该有 6–12 条，且**能覆盖 §3.3 表里的那 8 类缺口**（不必逐字一致，但类别要对）
3. 「下一步」应该指到**文件行号**（形如 `L269-L283`）并**点名要解掉的未决点**，而不是「建议阅读第 X 节」

### 5.4 常见问题

**Q：Skill 一定要联网吗？**
不用。全部运行离线完成；材料不足时标 `absent` / `undetermined`，不靠联网补。

**Q：没有 GPU / 没装 PyTorch 能跑吗？**
能。这是**阅读判断**类 Skill，不跑训练、不装框架、不下载数据集。

**Q：换一篇论文能用吗？**
能，但请**重新写死读者约束**（算力、预算、数据规模、目标）。约束变了，结论就会变——这正是案例 B 演示的：同一份 Skill 换主文档、换指标口径、换算力形态、换目标之后，得出的结论**理由完全不同**（A 是「单卡跑不动但 8 卡 4 小时内可跑」，B 是「研究循环机制可迁但作者出厂配置不可迁」，因为原文示例语料占 44 GiB，是读者 8GB 卡的 5.5 倍）。

**Q：为什么一次运行只跑一个案例？**
每个案例对应一个真实的阅读问题。跨案例的证据一致性能不能成立，是另一层问题——我另外做了跨案例的定位一致性核对（与案例 A 的 18 处重叠引用逐条比对，**真定位冲突 0 处**）。

## 6. 方法适用边界：什么场景该用、什么场景别用

量表里「技术深度」问的不只是"你做了什么"，还有"**为什么这样设计**"。这一节是方法本身的边界。

### 6.1 适用

- **核心问题形态是"能不能迁"**，而不是"这篇讲了什么"：你有一个具体的读者约束（算力、预算、数据规模、目标），要判断某套方法在那个约束下是否成立。
- **材料是可定位的公开说明文档 + 代码**：能被引文定位、能被程序化校验。方法描述散落在正文、表格与代码常量里，正是本流程的用武之地。
- **约束可以事先写死**：读者约束必须在运行前固定，否则"合不合适"就变成事后找理由。
- **产出需要被别人复核**：每条结论都带引文与定位，读者/评审不必相信你也能自己查。

### 6.2 不适用

| 场景 | 为什么不适合 | 该做什么 |
|---|---|---|
| **方法正确性验证** | 本流程只判断"能不能迁"，不跑对照实验，不产出性能数字 | 跑对照实验，本文里的 pilot 建议（§3.2 第 2 条）就是交接点 |
| **数据集许可 / 合规 / 隐私** | 流程不评估法律与合规风险 | 单独走法务与数据治理评估 |
| **需要领域专家判断的内容** | 临床、法务、伦理结论不在"可引文 + 可定位"的射程内 | 请领域专家，本文只做证据组织 |
| **只有二手转述、没有原文** | 没有原文就没有可校验的引文，整个流程失去地基 | 先拿到原文（论文、官方文档、源码） |
| **材料本身错乱** | 本流程会**如实报出**错乱（如 §4.3、§4.4），但无法修复 | 先修复材料，或把它当作异常案例单独处理 |

### 6.3 规模边界（这条我没验证过，属于诚实声明）

材料在 **1 篇文档 + 配套代码**的量级上，本流程的核验成本可控。若一次要处理几十篇论文，我预期会退化：**引文核验是逐条程序化比对，成本随材料量线性上升**。我**没有实测**这个上限，所以不宣称它成立——如果你的场景超过一篇，建议按"一个阅读问题一组材料"切片，而不是一次性喂一大批。

### 6.4 一个刻意的取舍：它会**拒绝**给出漂亮结论

当材料不足以判定时，正确的产出是 `undetermined` + "需要什么才能定"，而不是一个笃定的四选一。§3.3 那 8 个空白点就是这个设计的直接产物——**它们看起来像"没做完"，其实正是这份材料能支撑的边界**。

如果你的场景要求"必须给结论、不能有空白"，这个方法**不适用**。

## 7. 如果你要在玻尔科学空间里用这个方法

> **如实声明**：本次分享的**全部实践未在玻尔科学空间执行**。七次运行都在 MiniMax Code + MiniMax-M3.1-Flash 下**离线**完成（0 次外网请求）。所以这一节是**迁移指南**，不是使用记录——它给的是"该怎么搬"，不是"我搬过并验证了"。

本方法**不依赖任何特定平台**，它的全部输入是「一份文档 + 一组约束」，全部输出是 5 个纯文本文件。搬过去要做的只有两件事：

**第一步：把 Skill 挂进玻尔科学空间。** 把 `paper-method-fit-check/SKILL.md` 作为系统提示或项目规则放入，让助手在每次文献阅读时都按它工作流走。

**第二步：按同样的四段式提问。** 在玻尔科学空间里围绕论文提问时，**显式给出读者约束**并要求三类陈述分标：

```
读 paper-method-fit-check/SKILL.md，用它的"方法适用性核查"流程处理下面这篇论文。

【读者约束】8 × A100 80GB；单次训练 ≤ 4 小时、云卡 ≤ $100；数据可下载（磁盘 ≥ 100GB，
下载时间需单独说明）；不允许多机；只要方法机制，不要求复现最终数字。

【必须分标】论文原述 / 模型输出 / 你的判断，三者分别标注；引用给页码或行号。
【必须标注】材料没说清的地方标 absent 或 undetermined，并写明"需要什么才能定"。
【产出】四段结论 + 硬前置条件表 + 可程序化核验的引文索引 + 下一步阅读指向。
```

**注意**：在玻尔科学空间里跑同一条流程时，**核验环节要照做**——让助手把每条引文在原文里检索命中（而不是只写"见原文"）。§4.1、§4.2 讲的两个坑（渲染视图失真、CRLF 失配）在任何平台上都会出现；`scripts/check_agreement.py` 与 `scripts/extract_quotes.py` 都是纯标准库脚本，换环境后可直接重跑。

**如果玻尔侧的文件读取/引用能力与本地不同**，`source.txt`（字节精确、保留 CRLF）这份中间产物仍然要生成——它是让引文可被朴素子串搜索命中的关键。
